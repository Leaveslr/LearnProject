# 知识库操作手册

这份手册说明如何日常使用这个 Obsidian + Markdown 知识库。核心思路是：先低成本收集，再定期整理，最后把有价值的内容沉淀成自己的知识。

## 1. 打开方式

用 Obsidian 打开这个文件夹：

```text
/Users/didi/Documents/LearnProject/Knowledge
```

也可以用 VS Code 打开同一个文件夹，用来批量搜索、修改、重命名和配合 Codex 整理。

## 2. 日常收集流程

每天看到值得保存的内容时，先放进 `Inbox/`，不要急着分类。

适合放进 `Inbox/` 的内容：

- 文章链接
- 书摘
- 临时想法
- 技术问题
- 项目灵感
- 以后想研究的问题
- 和别人聊天时得到的启发

推荐新建类似这样的文件：

```text
Inbox/2026-04-29 零散记录.md
```

内容可以很粗糙，例如：

```md
# 2026-04-29 零散记录

## RAG

今天看到一个说法：RAG 更像是让模型带着资料回答问题，而不是让模型记住所有东西。

来源：https://example.com

## 想研究

- Obsidian 如何配合 Codex
- Markdown 知识库如何长期维护
```

这个阶段只追求记录下来，不追求格式漂亮。

## 3. 整理流程

建议每周整理一次 `Inbox/`，每次 20 到 40 分钟即可。

整理时按下面顺序处理：

1. 打开 `Inbox/`。
2. 看每条内容属于哪一类。
3. 移动或改写到对应目录。
4. 补一句话总结。
5. 加标签。
6. 补相关链接。
7. 更新 `Index.md` 或相关 MOC。

分类规则：

- 概念、方法、问题：放到 `Notes/`
- 文章、工具、文档链接：放到 `Links/`
- 具体目标或任务：放到 `Projects/`
- 某个主题的目录页：放到 `MOCs/`
- 每日流水记录：放到 `Daily/`

## 4. 写长期笔记

长期笔记放在 `Notes/`，建议用 `Templates/Note.md` 的结构。

一篇好的长期笔记通常包含：

- 标题清楚
- 一句话说明它是什么
- 3 到 7 条要点
- 来源
- 相关笔记
- 标签

示例：

```md
---
type: note
status: evergreen
created: 2026-04-29
tags:
  - AI
  - RAG
---

# RAG

一句话：
RAG 是让模型在回答前检索外部资料，从而减少只靠模型记忆带来的不可靠。

## 要点

- 检索阶段负责找到相关资料。
- 生成阶段负责组织答案。
- 适合知识变化快、需要引用来源的场景。

## 来源

- https://example.com

## 相关

- [[Embedding]]
- [[向量数据库]]
- [[知识库问答]]
```

## 5. 保存链接

链接不要只保存 URL。每个链接至少写清楚它为什么值得保存。

推荐放在 `Links/`，使用 `Templates/Link.md`。

示例：

```md
# SQLite 官方文档

链接：https://sqlite.org/docs.html

为什么保存：
查询 SQLite 行为时，官方文档比普通博客更可靠。

## 摘要

- 适合查 SQL 语法、事务、数据类型和命令行工具。

## 可转化成自己的知识

- SQLite 的类型系统
- SQLite 的事务行为

## 相关

- [[数据库]]
- [[SQL]]
```

## 6. 使用 MOC 组织主题

MOC 是 Map of Content，也就是主题索引页。它的作用不是写完整文章，而是把一个主题下的内容组织起来。

适合创建 MOC 的情况：

- 某个主题下已经有 5 篇以上笔记。
- 你正在系统学习一个方向。
- 某个主题长期反复出现。

示例：

```md
# AI Agent MOC

## 核心概念

- [[Agent]]
- [[Tool Calling]]
- [[Memory]]
- [[RAG]]

## 实践问题

- [[如何设计 Agent 工作流]]
- [[Agent 什么时候需要长期记忆]]

## 参考链接

- [[OpenAI Agents SDK 文档]]
```

## 7. 每日记录

如果当天只是零碎记录，可以放在 `Daily/`。

推荐命名：

```text
Daily/2026-04-29.md
```

可以记录：

- 今天学到什么
- 遇到什么问题
- 有什么想法
- 哪些内容需要以后整理

每日记录不需要完美，它的价值是留下线索。

## 8. 和 Codex 配合

Codex 可以帮你做重复、批量、整理类工作。你可以直接让 Codex 读取这个目录里的 Markdown 文件。

常用请求：

```text
请整理 Knowledge/Inbox 里的内容，把它们移动到合适目录，保持 Obsidian 双链格式。
```

```text
请帮我找出 Knowledge/Notes 里没有来源的笔记。
```

```text
请基于 Knowledge/Notes 里和 AI 有关的笔记，生成一个 AI 学习 MOC。
```

```text
请把 Knowledge/Links 里的链接整理成摘要，并标出哪些值得转成长期笔记。
```

```text
请检查这个知识库里是否有重复主题或可以合并的笔记。
```

当你让 Codex 整理时，可以提醒它遵守：

```text
请按照 Knowledge/Codex.md 的规则整理。
```

## 9. 每周维护清单

每周找一个固定时间，执行一次轻量维护。

建议清单：

- 清理 `Inbox/`
- 把重要内容改写成自己的话
- 给新笔记补来源
- 给新笔记补标签
- 给相关笔记添加双链
- 更新 `Index.md`
- 如果某个主题内容变多，创建或更新 MOC

每周不需要把所有东西整理完。只要让系统比上周更清楚一点，就已经很好。

## 10. 命名建议

文件名尽量直接、可搜索。

推荐：

```text
RAG.md
SQLite 类型系统.md
AI Agent MOC.md
如何整理 Inbox.md
2026-04-29.md
```

不推荐：

```text
未命名.md
新建文档 1.md
一些想法.md
资料.md
```

## 11. 标签建议

标签不要太多，先保持克制。

常用标签：

- `#todo` 待处理
- `#idea` 想法
- `#question` 问题
- `#reference` 参考资料
- `#project` 项目相关
- `#evergreen` 长期有效

如果一个标签只用了一次，通常可以先不用它。

## 12. 最小可持续流程

如果你不想维护复杂系统，只执行这三个动作就够了：

1. 平时所有东西先丢进 `Inbox/`。
2. 每周把最重要的 3 到 5 条整理成 `Notes/`。
3. 每月为一个高频主题创建或更新一个 MOC。

这个知识库的目标不是收藏更多东西，而是让重要信息逐渐变成你自己的判断、方法和问题库。
