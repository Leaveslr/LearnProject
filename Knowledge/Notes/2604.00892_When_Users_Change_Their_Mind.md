# When Users Change Their Mind: Evaluating Interruptible Agents in Long-Horizon Web Navigation

- arXiv: [2604.00892](https://arxiv.org/abs/2604.00892)
- PDF: `paper/2604.00892_When_Users_Change_Their_Mind.pdf`
- 日期：2026-04-01
- 主题：可中断 Agent、长程网页导航、WebArena-Lite、用户意图变更

## 一句话总结

这篇论文提出 InterruptBench，用 WebArena-Lite 的长程网页导航任务系统评估 LLM Agent 在执行过程中被用户打断、补充、纠正或撤回需求时，能否把新的用户意图真正落实到后续网页状态和最终答案中。

## 研究动机

现有 Web Agent 评测通常默认用户需求在任务开始后不再变化，但真实使用中，用户很可能在长任务执行中途改变主意，例如补充约束、纠正说错的条件，或撤回一部分要求。

这类中断很难处理，因为网页导航任务不是纯文本对话：Agent 的点击、输入、跳转会改变环境状态。如果用户中途修正目标，Agent 不只要“听懂新话”，还要检查当前页面状态是否已经带着旧假设继续执行，并在必要时回退、修改、重新计算。

## 核心贡献

1. 提出 InterruptBench：第一个面向长程、环境约束网页导航任务的用户中断评测集。
2. 定义三类真实中断：
   - Addition：用户补充新的要求或约束。
   - Revision：用户纠正先前说错的信息。
   - Retraction：用户撤回之前给出的部分细节或限制。
3. 设计轨迹驱动的中断模拟：先跑初始请求得到完整轨迹，再按相对进度注入中断，继续观察 Agent 是否能适应新意图。
4. 不只看最终成功率，还分析中断后多少步内成功、动作成本、输出 token 成本，以及多轮中断下的性能变化。

## Benchmark 构造

论文基于 WebArena-Lite 的 165 个高质量人工验证任务，覆盖 5 类网页环境：

- Reddit / 社交论坛
- GitLab / 协作代码平台
- CMS / 电商内容管理
- Map / 地图
- OneStopShop / 在线购物

每个任务由强模型合成初始用户请求和中断消息，并要求满足三个约束：

- Ground Truth Consistency：初始请求加上中断后的完整意图，必须等价于原始 WebArena-Lite 任务，最终答案一致。
- Necessity：每条中断消息都必须是必要的，缺少它会导致不同的正确答案。
- Authenticity：中断消息要像真实用户自然发出的补充、纠正或撤回。

## 实验设置

评测模型包括 Claude Haiku 4.5、Claude Sonnet 4.5、Claude Opus 4.5、Qwen 系列、DeepSeek-V3.1、Mistral-Large-3，统一放在 WebAgent-R1 的 Agent 框架中。

默认在基线轨迹 60% 位置注入中断。评价指标主要有：

- Success Rate：是否完成最终的用户意图。
- SR(k)：中断后 k 个动作内的成功率，用来观察 Agent 适应中断的速度。
- 动作数与输出 token 数：衡量中断后的恢复成本。
- 多轮中断成功率：用户连续给 1、2、3 次必要更新时，Agent 是否能逐步利用更多信息。

## 关键结果

### 1. 中断后前 10 步最关键

论文发现，大多数模型的成功率在中断后约 10 个动作内快速上升，之后趋于平台期。这说明 Agent 能不能及时适应更新，通常很早就能看出来。

在 Addition 场景中，Claude Opus 在 k=30 时约达到 55% 成功率，Sonnet 约 44%，Haiku 约 38%；开源/开放权重模型整体更低，Qwen、DeepSeek、Mistral 大约在 23%-30% 区间。

### 2. Revision 最依赖真正理解中断

Revision 场景里，没有接收中断的基线几乎无法成功，因为用户一开始给的是错误条件。只有 Agent 能正确把“纠正信息”覆盖到当前执行状态，才可能完成最终目标。

Addition 的基线表现稍好，因为补充信息有时不完全破坏原计划；Retraction 的基线更强一些，因为撤回约束可能让任务变简单，差距主要体现在更快完成，而不是最终上限大幅提升。

### 3. 成本主要来自 token，而不是动作数

中断后动作数变化通常不大，但输出 token 成本可能显著增加。说明 Agent 为了整合新要求会花更多“思考成本”，即使实际网页操作数量差不多。

失败-失败的样本成本最高：模型既没完成任务，还消耗更多 token 和动作去反复重规划。论文把这解释为“无效恢复”或“低质量重规划”。

### 4. 中断可能帮忙，也可能伤害

在 Addition 场景中，很多任务属于 F/S：没有中断时失败，有中断后成功。强模型恢复能力更明显，Opus 有 70 个这类恢复案例，Sonnet 有 55 个。

但也存在 S/F：没有中断本来会成功，收到中断后反而失败。虽然数量不多，但很重要，因为这说明中断会让 Agent 把旧计划和新意图混在一起，导致原本可完成的任务被搞坏。

### 5. 多轮中断通常有帮助，但不稳定

当用户连续提供 1、2、3 条必要信息时，整体成功率通常上升。Claude 系列提升最稳定：Opus 从 1 次中断的 21.21% 提升到 3 次中断的 41.82%，Sonnet 从 15.15% 提升到 41.21%。

开放权重模型提升较小且更不稳定。DeepSeek-V3.1 从 2 次中断到 3 次中断略有下降，说明后续更新有时会干扰已经整合的信息。

## 案例启发

论文的 Map 案例很典型：用户原本让 Agent 比较去 CMU 的步行和驾车时间，中途补充起点应为 Randyland。失败轨迹只是表面上承认了这个补充，却没有修改页面里的起点字段，最后仍基于旧路线回答。成功轨迹则会识别意图漂移，修改 From 字段，重新计算路线，再输出答案。

这里的关键不是“最终回答里有没有提到新要求”，而是 Agent 是否把新要求传播到了环境状态、页面字段、已有中间结果和后续动作中。

## 我的理解

这篇论文真正抓住了可中断 Agent 的核心难点：中断不是一条新的 prompt，而是一次执行状态迁移。Agent 需要维护三层一致性：

- 用户意图一致性：现在到底要做什么，不再做什么。
- 环境状态一致性：网页里哪些字段、筛选器、查询结果还是旧意图留下的。
- 计划一致性：后续动作是否仍沿用旧目标，是否需要回退、重算或局部修补。

对实际 Agent 系统设计来说，只靠更强模型可能不够。更可靠的方案可能需要显式的 intent diff、状态检查点、可回滚操作、页面状态审计，以及在中断后强制执行“旧假设清理”流程。

## 局限与疑问

- 中断消息由模型合成后人工审核，真实性比纯合成更好，但仍不等同于真实用户在线交互。
- WebArena-Lite 只有 165 个任务，覆盖面有限。
- 论文主要衡量任务成功与成本，还可以进一步分析不同 UI 状态、不同错误类型、不同回滚策略对中断恢复的影响。
- 论文中模型命名在正文和表格里出现了 Qwen 版本表述不完全一致的情况，复现实验时需要核对代码仓库配置。

## 可借鉴点

如果要做自己的 Agent 评测或系统改进，可以参考这几个设计：

- 把用户中断拆成 Addition、Revision、Retraction，而不是笼统叫“用户反馈”。
- 用中断后 k 步成功率衡量恢复速度，比只看最终成功率更有诊断价值。
- 对比 matched no-interruption baseline，才能看出中断到底是帮助、伤害还是只是改变成本。
- 在失败分析中检查 Agent 是否真的修改了环境状态，而不是只在语言层面承认新意图。
