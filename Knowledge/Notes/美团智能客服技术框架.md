# 美团智能客服技术框架

一句话：
美团 WOWService 把智能客服从“会回答的对话模型”升级成“可理解业务、可调用工具、可跨场景协作、可自动评测迭代”的工业化智能交互系统。

## 本地资料

- PDF：[[Higher Satisfaction, Lower Cost- A Technical Report on How LLMs Revolutionize Meituan’s Intelligent Interaction Systems.pdf|本地 PDF]]
- arXiv：https://arxiv.org/abs/2510.13291

## 这篇论文要解决的问题

本地生活服务场景里的客服不是简单 FAQ，而是高并发、多轮、多角色、多规则的服务流程。用户、商家、骑手之间的信息流动很复杂，业务规则又频繁变化，所以系统面临几个核心难题：

- 冷启动数据难构造，人工标注成本高，系统自迭代能力弱。
- 多轮对话中，意图理解、规则遵守、方案提取和情绪安抚都容易出错。
- 业务知识和规则变化快，纯数据驱动模型迁移成本高。
- 单一 LLM 难以覆盖外呼、跨场景流转、图片/语音理解等复杂任务。
- 多轮开放对话没有统一标准答案，难以稳定自动评测和持续优化。

## 总体框架

论文提出的 WOWService 可以拆成五层：

```text
数据与知识层
    ↓
基础模型训练层：CPT → SFT → DPO → RL
    ↓
业务样本与知识注入层：数据驱动 + 知识驱动 + RAG + 工具调用
    ↓
Agent 协同层：主 Agent + 专用子 Agent
    ↓
评测与回流层：在线质检、离线坏例、自动评测、回归测试
```

我的理解是：它的关键不是“用了一个更强的大模型”，而是把客服系统做成了一个可运营的闭环。模型能力、业务知识、在线质检、坏例修复、Agent 工具化、评测平台共同形成持续改进飞轮。

## 1. 数据与知识层

### 数据来源

WOWService 同时使用多类数据：

- 通用语料，用于保持基础能力，避免领域继续预训练导致通用能力退化。
- 业务领域数据，包括知识库、服务记录、服务规范等。
- 人工客服真实对话，用于学习自然沟通、服务流程和情绪表达。
- 知识驱动生成数据，用于把业务规则、流程、工具调用显式注入训练样本。
- 线上自采样数据，用于 SRT 自我精炼和坏例回流。

### 知识生产

论文强调知识要被拆成最小原子单元，而不是把一个完整流程塞进一条大知识。每个知识单元至少包含：

- 背景上下文：这条知识适用于什么业务场景。
- 高频用户问题：帮助检索和场景匹配。
- 解决方案脚本：明确该如何处理用户诉求。

知识类型包括 Q&A 咨询、规则文档、流程知识和碎片知识。涉及工具调用时，还会有统一的工具描述和输出格式。

## 2. 模型训练层

### 总流程

WOWService 的训练流程不是简单地“CPT → SFT → DPO → RL”线性跑一遍，而是一个由业务数据、知识库、线上反馈和评测系统共同驱动的持续迭代过程：

```text
基础模型
    ↓
CPT：领域继续预训练
    目标：注入客服领域知识，同时保住通用能力
    输入：通用语料 + 领域语料
    输出：具备客服领域基础能力的 base model
    ↓
SFT：监督微调
    目标：对齐客服对话风格、业务流程、工具调用格式
    输入：
        - 数据驱动样本：人工客服真实对话
        - 知识驱动样本：业务知识/规则/流程/工具生成样本
        - 通用指令数据
    样本构造方式：
        数据-知识双驱动适配
        用 Prompt 对齐、三层一致性检查、知识注入和 CoT 蒸馏，
        让模型同时学习自然客服表达和业务规则遵循
    输出：能“说 + 做”的客服 Agent 初始模型
    ↓
DPO：偏好学习
    目标：修复线上坏例，让模型偏向更符合客服标准的回复
    输入：原始坏回复 rejected + 重写/人工优质回复 chosen
    输出：更少幻觉、重复追问、错误方案和流程停滞的模型
    ↓
RL：推理增强
    目标：强化复杂规则遵循、知识引用、方案正确性和人性化表达
    输入：复杂指令数据、知识驱动 CoT、规则奖励、GRM 奖励
    输出：更会按业务规则推理，也更会安抚和推进对话的模型
    ↓
上线服务
    ↓
SRT + 评测回流
    目标：从线上 self-sampled data 中挖掘 Good/Bad Cases，进入下一轮 SFT/DPO/RL
    输入：线上对话、工具调用、质检结果、用户满意度、人工/自动评测
    输出：新一轮训练数据、坏例库、回归集、评测报告
    ↺
返回 SFT / DPO / RL 持续迭代
```

各阶段的关系可以这样理解：

| 阶段 | 主要解决什么 | 和下一阶段的关系 |
|---|---|---|
| CPT | 让模型懂客服领域，但不丢通用能力 | 给 SFT 提供更好的领域底座 |
| SFT | 学会客服话术、流程和工具调用格式 | 产出可上线/可采样的初始策略模型 |
| 数据-知识双驱动 | SFT 阶段的业务样本构造与知识注入范式 | 后续帮助定义 DPO 坏例，也为 RL 的知识遵循奖励提供依据 |
| DPO | 修复具体线上坏例和偏好问题 | 把运营发现的问题转成模型偏好 |
| RL | 强化复杂推理、规则遵循和人性化表达 | 提升多约束业务场景下的稳定性 |
| SRT / 评测回流 | 从真实服务中发现好样本和坏样本 | 形成下一轮 SFT/DPO/RL 数据 |

所以，CPT 和 SFT 更像“能力底座建设”；数据-知识双驱动不是和 SFT/DPO/RL 并列的新训练阶段，而是 SFT 阶段的业务样本构造与知识注入方式，并持续影响 DPO 的坏例定义、RL 的奖励设计和线上推理；DPO 和 RL 更像“线上行为修复与强化”；SRT 和评测回流则让整个训练流程变成可持续运转的飞轮。

### CPT：领域继续预训练

CPT 的目标是让基础模型具备客服领域知识，同时尽量不损伤通用能力。

#### 通用能力与领域能力平衡（论文 2.1.1）

继续预训练的核心矛盾是：

```text
领域数据比例太高：
    客服领域能力提升更明显，但容易覆盖原有知识，造成灾难性遗忘。

通用数据比例太高：
    通用能力更稳定，但客服领域能力提升不足。
```

论文把数据配比调参做成了一个低成本预测流程，而不是直接在大模型上反复试错：

```text
1. 准备多源数据
   通用数据 + 客服领域数据。
   领域数据包括知识库、服务记录、服务规范等。

2. 随机生成多组数据混合比例
   例如通用 70% / 领域 30%，通用 80% / 领域 20% 等。

3. 训练小规模 proxy model
   每一种数据配比训练一个小模型，用低成本观察不同配比的效果。

4. 在验证集上计算 loss
   每个 proxy model 训练完成后，都在验证集上评估 loss。

5. 拟合回归模型
   输入是数据配比向量，输出是验证集 loss。
   也就是学习“什么样的数据比例更可能带来更低 loss”。

6. 扩大候选配比空间
   在更大的模拟空间里生成更多候选数据比例。

7. 用回归模型预测最优配比
   对候选比例预测 loss，选出预测效果最好的混合比例。

8. 用最优配比训练目标模型
   最后才把该比例用于 LongCat / Yi-34B / Qwen2.5-32B 等目标模型的继续预训练。
```

论文提到，相比人工调参，这种方式效率提升超过 75%。实验中大约 **80% 通用数据 + 20% 领域数据** 时，可以取得较好的平衡：通用能力退化较小，同时客服领域能力明显增强。

同时，它用小规模预训练和 PPL 变化评估不同数据源质量，提升数据源筛选效率。

### SFT：轻量高质量微调

SFT 阶段从“百万级样本”转向“少量高质量样本”。论文发现，在有充分 CPT 的基础上，少于 1 万条高质量样本就能接近百万级数据效果，训练成本下降 99%，迭代频率提升到每周 3-4 个版本。

SFT 的另一个重点是统一“说”和“做”：

```json
{
  "response": "给用户看的回复",
  "tool_call": "模型要执行的工具指令"
}
```

这样可以避免过去“对话模型负责说、分类模型负责工具”的说做不一致，也能降低延迟和机器资源。

### DPO：面向业务坏例的偏好学习

DPO 对应论文 2.3 Preference Learning Stage。它的目标是用“更好回复 vs 更差回复”的偏好对，把客服场景里很细的质量标准注入模型，例如清晰、专业、共情、能推进流程。

在 DPO 里，一条训练数据可以抽象成：

```text
x：用户问题 + 对话历史 + 场景信息
y+：更高质量回复 chosen
y-：较差回复 rejected
```

训练目标不是单独训练 reward model，而是直接提高模型生成 `y+` 的概率、降低生成 `y-` 的概率。这样比传统 RLHF 链路更轻，适合客服系统高频迭代。

#### 领域坏例类型（论文 2.3.1）

论文列出的典型问题包括：

- 没有澄清用户真实诉求。
- 反复询问用户已经说过或系统已经知道的信息。
- 幻觉，给出没有依据的信息。
- 话术重复，无法推进问题。
- 给出错误方案。
- 应补偿但没有主动补偿。
- 有补偿信号但没有遵守。
- 无法推动处理流程。

这些问题的共同点是：它们会直接影响用户满意度、解决率和转人工率。有些问题不一定是语言不流畅，而是客服业务动作错了，比如该补偿没补偿、该澄清没澄清、该推进流程却停在原地。

#### Operational DPO 流程（论文 2.3.2）

论文里的 DPO 不是一次性离线训练，而是一个运营化闭环：

```text
1. Identification
   持续识别线上坏例，例如幻觉、重复追问、错误方案、未触发补偿。

2. Rules Summarization
   运营和训练人员总结这些坏例背后的质检规则。

3. Rules & Cases Test
   测试规则能否稳定识别问题。
   如果是正则规则，要覆盖边界 case；
   如果是 LLM 检测 prompt，要持续优化提示词。

4. Automatic Quality Inspection
   在 self-sampled data 上自动质检，挖掘更多同类坏例。

5. Data Annotating
   人工标注员、模型和规则系统联合标注，筛选可用训练样本。

6. Data Construction
   构造偏好数据：同一个输入下，标注 preferred / dispreferred 回复。

7. DPO Training
   用偏好对训练模型，让模型学习最新业务规则和客服质量偏好。

8. Regression Testing
   做自动和人工回归测试，确认新模型修复坏例，同时不遗忘历史能力。

9. Model Deployment
   上线新模型，继续进入下一轮坏例发现和修复。
```

论文报告，Operational DPO 能明显提升多类坏例修复率，例如幻觉问题修复率达到 97.5%，错误方案修复率从 65.51% 提升到 100%，无法推进流程从 83.41% 提升到 100%。

#### DPO 例子：用户已经给了订单号，模型还重复追问

用户说：

```text
订单 123456，骑手已经超时半小时了，我要处理一下。
```

较差回复 `y-`：

```text
请您提供一下订单号，我帮您查询。
```

问题：

- 用户已经提供了订单号，模型重复询问。
- 没有承接用户的超时诉求。
- 没有推进查询和处理流程。

更好回复 `y+`：

```text
我看到你提供的订单号是 123456，也理解你已经等了很久。我先帮你查询这单的配送状态和是否满足超时处理条件，请稍等。
```

偏好样本可以写成：

```text
x = 用户问题 + 对话历史 + 已识别订单号信号
y+ = 承认订单号、安抚用户、推进查询的回复
y- = 重复追问订单号的回复
```

DPO 学到的是：当系统已经有订单号信号时，不要重复索取信息，而要承接已有信息并推进下一步。

### RL：复杂规则遵循与人性化表达

RL 对应论文 2.4 Reasoning Enhancement Stage。它不只是在“让回答更好听”，而是解决两个更难的问题：

- 复杂业务规则下，模型是否能稳定遵守多约束、多任务、多流程。
- 开放式客服对话里，模型是否能更自然、更有人情味，而不是机械重复。

论文分成两条线：

1. 规则和知识遵循
   对可验证任务，用规则奖励；对不可验证复杂指令，用原则型评测模型自动打分。奖励包括方案正确性、知识引用正确性、对话适当性、重复惩罚和 CoT 长度惩罚。

2. 人性化和情绪关怀
   对开放式对话，用 GRM 作为奖励模型，把对话分成澄清、解决、收尾三个阶段分别评分，再用 RL 优化策略模型。目标是减少机械重复，提高自然度、安抚感和问题解决率。

#### Reasoning Enhancement 总流程（论文 2.4）

Reasoning Enhancement Stage 可以理解成一条从“复杂业务指令数据”到“规则奖励 + 人性化奖励”的训练路线：

```text
1. 定义复杂指令类型
   把客服中的复杂任务拆成多约束、多任务、复杂知识注入三类。

2. 挖掘和合成训练数据
   从业务指令数据中自动标注复杂样本；
   对缺失类型，用角色、约束、任务分支等方式合成。

3. 筛选种子数据
   按正确性、完整性、简洁性过滤低质量样本。

4. 评估样本难度
   让不同能力模型回答同一问题；
   过滤过于简单、区分度不高的样本。

5. 生成和筛选 CoT
   用强推理模型生成推理链；
   可验证样本对比标准答案；
   不可验证样本多次采样，再选择更优结果。

6. SFT 冷启动
   用数据驱动样本 + 知识驱动 CoT 样本训练，
   让模型学会基本客服对话和业务规则推理路径。

7. RL 强化规则遵循
   在 SFT 模型基础上继续训练，
   用 Rsol、Rkn、Rdlg、Rcot 约束方案正确性、知识引用、对话适当性和推理长度。

8. GRM 强化人性化表达
   对开放式客服对话，按澄清、解决、收尾三个阶段评分，
   让模型学会先承接情绪、再解释规则、最后推进下一步。
```

这条流程的目标是把模型从“生成一个看似合理的答案”，强化成“按业务规则推理，并按客服服务标准沟通”。

#### 复杂指令与知识遵循增强（论文 2.4.1）

美团客服场景里的复杂指令被分成三大类：

| 类别 | 例子 |
|---|---|
| Multiple Constraints | 指定风格、指定情绪、指定内容、指定回复格式、数据约束、角色扮演 |
| Multiple Tasks | 串行多任务、并行多任务 |
| Complex Knowledge Injection | 应用业务知识、遵守复杂流程、理解状态信号、理解长对话 |

具体流程是：

```text
1. 数据挖掘和合成
   用复杂指令分类体系，从业务指令数据中自动标注和挖掘样本。
   对缺失类型，通过角色、分支数、约束、任务类型等维度合成数据。

2. 种子数据筛选
   从正确性、完整性、简洁性等维度打分，去掉低质量或不合逻辑样本。

3. 难度评估
   让不同能力模型对同一指令采样回答并投票。
   过于简单、模型表现差异不大的样本会被过滤。

4. CoT 生成和筛选
   用强推理模型生成回答和思维链。
   对可验证数据，比较预测和标准答案，保留一致的思维链。
   对不可验证数据，多次采样后由模型选择更优结果。

5. 强化学习
   可验证任务用规则匹配算 reward。
   不可验证任务用原则型评测模型打分，例如 SPCT 生成评估原则，再由评测模型评分。
```

#### 业务知识推理的 RL 流程

在智能客服业务里，论文还进一步把数据驱动和知识驱动结合起来做 RL：

```text
1. 先用 SFT 冷启动
   训练集包含数据驱动样本和带 CoT 的知识驱动样本。

2. 让模型学会两件事
   - 常规客服对话怎么说。
   - 背后的业务知识和规则推理路径是什么。

3. 重新引入知识驱动 CoT 数据
   在 SFT 模型基础上继续做 RL。

4. 用规则奖励约束输出
   奖励函数：
   Rtotal = Rsol + Rkn + Rdlg + Rcot
```

各项奖励含义：

| 奖励 | 含义 |
|---|---|
| Rsol | 方案正确性，方案和标准答案一致得高分 |
| Rkn | 知识引用正确性，是否引用正确知识 ID |
| Rdlg | 对话适当性，包含重复惩罚和答案相似度 |
| Rcot | CoT 长度惩罚，避免推理过长或过短 |

其中重复惩罚会检查当前回复和历史对话的 Jaccard 相似度、最长公共子串比例，防止模型反复说同一句话。

#### 人性化对话与情绪关怀增强（论文 2.4.2）

规则奖励适合有明确答案的任务，但客服里大量问题是开放式对话：怎么安抚、怎么解释、怎么收尾，并没有唯一标准答案。因此论文引入 GRM 作为奖励模型。

GRM 评估会把对话分成三个阶段：

| 阶段 | 关注点 |
|---|---|
| Clarification | 是否承接上下文、总结已有信息、明确还缺什么 |
| Solution | 是否有效推进处理，方案是否清楚 |
| Wrap-up | 是否有合适结束语，是否自然收尾 |

流程是：

```text
1. 从 self-sampled data 中抽取历史对话。
2. 按澄清、解决、收尾三个阶段切分。
3. 为每个阶段设计多维评分标准。
4. 每个维度输出 0/1，再归一化成 0-1 reward。
5. 用训练好的 GRM 给 rollout 打分。
6. 结合格式分等信号，用 GRPO/DAPO 类方法训练 policy model。
```

论文提到，训练后的 GRM 与人工标注一致率超过 85%。使用 Trained GRM + RL 后，FSR、UR、Accuracy 等指标优于未训练 GRM 和 BGE 基线。

#### 高质量回复重写

论文还做了“零标注高质量回复重写”：

```text
1. 从高质量对话语料中挖掘优质回复。
2. 通过降质改写生成负样本，例如机械、安抚单一、方案模糊。
3. 通过风格迁移，让回复保持原方案不变，但表达更自然、更有情绪价值。
4. 用 SFT + RL 训练重写模型。
5. 用 win rate 和 plan consistency rate 评估：
   - win rate：重写回复是否优于原回复。
   - plan consistency：重写前后方案是否一致。
```

这部分的关键是：提升表达质量时不能改掉解决方案。客服里“说得更好”必须建立在“方案一致、规则不变”的前提下。

#### RL 例子：退款解释既要遵守规则，也要安抚用户

用户说：

```text
我付了 20 元，为什么只退我 12 元？这不合理吧。
```

业务知识：

```text
订单实付：20 元
现金支付：12 元
平台优惠券：5 元
商家优惠：3 元
规则：现金部分原路退回，优惠不按现金退；平台券按券规则退回或失效。
```

一个只做 SFT 的模型可能回复：

```text
因为优惠券和商家优惠不退现金，所以只能退 12 元。
```

这个答案方案大体正确，但体验一般：

- 没有承接用户质疑。
- 没有拆清楚 20 元到 12 元的来源。
- 没有说明用户下一步可以看哪里。

RL 中各项奖励会这样约束：

```text
Rsol：
    是否正确解释现金退款为 12 元。

Rkn：
    是否引用正确退款规则，而不是编造补偿规则。

Rdlg：
    是否避免重复，是否和高质量答案语义接近。

Rcot：
    推理是否足够说明金额拆分，但不过长。

GRM：
    是否先安抚，再解释，再给下一步。
```

更优回复是：

```text
我理解你看到付款 20 元但只退 12 元会觉得不对。我帮你拆一下：这单里现金支付部分是 12 元，另外 5 元是平台券、3 元是商家优惠。按退款规则，现金部分会原路退回，优惠不会按现金退，所以本次现金退款是 12 元。你可以在订单详情的退款明细里查看拆分；如果平台券按规则应退回但没有到账，我可以继续帮你核对。
```

这个回复同时满足：

- 业务推理正确。
- 引用规则正确。
- 情绪承接更自然。
- 给出下一步核对动作。
- 没有越权承诺补偿。

所以它会在规则奖励和 GRM 奖励上都更高。

## 3. 数据-知识双驱动样本构造

论文 2.2.2 的 Hybrid Data-Knowledge Driven Approach，首先应理解为 **SFT 阶段的业务样本构造与知识注入范式**，而不是一个和 SFT、DPO、RL 并列的独立训练阶段。

它的核心是把两类样本融合进同一个 SFT 训练框架：

- 数据驱动负责学习标准流程、自然表达、隐性服务经验。
- 知识驱动负责适应业务规则变化，保证可控性和可解释性。
- RAG 负责分钟级知识更新，减少重新训练成本。
- 模型在推理时先判断有没有可用知识，有则基于知识推理，没有则依靠参数内化能力生成回复。

关键点在于：知识不是简单拼进 prompt，而是通过训练数据、Prompt 对齐、一致性检查、知识注入、CoT 蒸馏和推理时 RAG 共同进入模型行为。

它对后续阶段也有影响：

- 对 DPO：帮助定义“没用知识、用错知识、说做不一致、违反新规则”等坏例。
- 对 RL：提供可验证的知识 ID、方案正确性、规则遵循等奖励依据。
- 对推理：让模型学会有知识就用知识，无知识时依靠内化能力，同时避免编造。

### 具体流程：数据-知识双驱动（论文 2.2.2）

论文里的 Hybrid Data-Knowledge Driven Approach 可以拆成三阶段：

```text
阶段 1：训练数据构造
    ↓
阶段 2：两阶段优化
    ↓
阶段 3：双模块推理
```

#### 阶段 1：训练数据构造

训练数据来自两类互补来源：

- 知识驱动数据：由知识驱动生成器基于业务知识、规则、流程和工具说明生成，通常带有推理链和可执行计划。
- 人工客服真实对话：来自人和人的服务记录，通常没有显式知识和推理链，但包含真实沟通方式、情绪表达和隐性经验。

为了把这两类数据放进同一个模型里训练，论文做了三件事：

```text
1. 三层一致性检查
   - 推理链 self-consistency：同一问题的推理是否自洽。
   - 规则冲突检查：推理和回复是否违反业务约束。
   - 回复-执行计划对齐：给用户的说法和实际要执行的动作是否一致。

2. Prompt 对齐
   把人工客服对话和知识驱动数据整理成一致的输入格式。
   这样模型不会把它们看成两种完全不同的任务。

3. 自适应推理
   推理时如果检索到了可用知识，就启用 CoT/业务推理；
   如果没有可用知识，就不强行展开推理，直接依靠模型内化能力生成回复。
```

#### 阶段 2：两阶段优化

第一步是 SFT：

- 训练数据中，领域数据占约 60%，包括操作数据和人工客服对话。
- 通用数据占约 40%，用于保持通用指令遵循、表达和推理能力。

第二步是基于规则的 RL：

- 使用已上线 SFT 模型回流的数据。
- 对知识引用、方案正确性、对话适当性、重复程度等维度设计奖励。
- 让模型不仅“知道规则”，还在生成时更稳定地遵守规则。

#### 阶段 3：双模块推理

线上推理时分成两个核心模块：

```text
1. 知识检索模块
   根据用户问题、订单/履约/售后信号、场景标签检索相关知识。

2. 回复生成模块
   先判断知识是否可用。
   如果可用：基于检索知识、业务规则和工具 schema 生成回复与动作。
   如果不可用：依靠模型已经内化的服务能力和历史对话生成回复。
```

这种设计的好处是：业务规则更新时可以通过 RAG 做分钟级更新，不必每次重新训练；而常见服务流程和自然沟通能力则保存在模型参数里。

### 四个落地组件

#### Prompt Engineering

Prompt 不只是普通系统提示，而是把客服执行所需的信息结构化放进去：

- 角色：当前模型扮演什么服务角色。
- 指令：本轮要完成什么任务。
- 约束规则：哪些事情不能做，哪些条件必须满足。
- 业务知识：检索到的知识内容。
- 方案列表：可选解决方案。
- 系统信号：订单状态、配送状态、售后状态、补偿信号等。
- 对话历史：用户已经说过什么，系统已经做过什么。

#### Knowledge Production

知识生产强调“原子化”。也就是把一个复杂流程拆成可独立维护的小知识单元。

每个知识单元至少包含：

- 背景上下文：适用场景。
- 高频用户问题：用于检索匹配。
- 解决方案脚本：具体处理方式。

如果涉及外部系统，还要补充工具描述和标准输出格式。

#### Knowledge Injection

知识注入有两种方式：

1. 批量检索
   给知识单元打场景标签，进入某个场景时一次性取回该场景下的一组知识。粒度粗一些，但覆盖更稳，检索难度更低。

2. 对话式内化
   从高质量自采样对话里继续训练模型，让常见流程、表达和隐性经验进入模型参数。推理时模型会在检索知识和参数记忆之间做平衡。

#### Data Quality Control

数据质量控制的核心是保证“知识可用、回复合规、推理可信”：

```text
1. 用规则和人工标注筛选符合业务约束的人类客服对话。
2. 用 LLM 判别器检查检索到的知识是否与当前对话相关。
3. 用第二个分类器检查原始客服回复是否遵守选中的知识。
4. 如果回复不合规，就重写回复，使其与知识和业务规则对齐。
5. 如果没有可用知识，就参考人工客服回复，避免模型凭空编造。
6. 把“选知识 → 用知识 → 生成回复”的过程蒸馏成 CoT 样本，用于训练模型。
```

### 一个例子：用户申请发票

假设用户问：

```text
我上周点的那单外卖怎么开发票？
```

系统里的流程大概是：

```text
1. 场景识别
   识别为“发票咨询/发票申请”场景。

2. 信号获取
   读取订单状态、订单时间、商家类型、是否已开票、是否支持平台开票等信号。

3. 知识检索
   检索“发票申请入口”“可开票时间范围”“商家开票/平台开票区别”“异常处理方式”等知识单元。

4. 知识可用性判断
   如果订单满足开票条件，就使用检索到的流程知识。
   如果订单不满足，比如超过可申请时间或该商家不支持平台开票，就切换到对应解释和替代方案。

5. 生成回复和动作
   模型生成自然语言回复，同时生成工具调用或操作计划。

6. 质检
   检查回复是否引用了正确规则，是否误导用户，是否说做一致。
```

可能的模型输出不是单纯一句话，而是“回复 + 动作”的统一结构：

```json
{
  "response": "这单可以申请发票。我帮你看了一下，入口在订单详情页的“开发票”。你进入上周那笔订单后，点击页面底部的开发票，按提示填写抬头和税号就可以提交。如果页面没有入口，我可以继续帮你确认商家是否支持开票。",
  "tool_call": {
    "name": "check_invoice_eligibility",
    "arguments": {
      "order_id": "当前订单",
      "scenario": "invoice_application"
    }
  }
}
```

这里数据驱动部分让模型学会自然解释和安抚用户；知识驱动部分保证它遵守发票规则；工具调用让它不只回答，还能实际检查订单是否可开票；质检和回流则负责发现“规则说错、入口说错、重复追问”等问题，进入下一轮 DPO/RL 修复。

## 4. SRT 自我精炼闭环

SRT 是 Self-Refinement Training，目标是让智能客服模型利用自己在线服务中产生的数据持续变好。论文强调它要解决三个问题：

- 训练数据主要来自人工标注记录，覆盖有限，离线训练效果和线上真实表现之间容易有落差。
- 业务场景和用户需求持续变化，模型如果没有自迭代机制，线上效果会随时间退化。
- 现有模型容易出现方案不准、语言不够拟人、表达重复、回复僵硬等问题，需要针对性增强。

### 整体流程

SRT 的闭环可以理解成：

```text
线上模型服务用户
    ↓
产生 self-sampled data
    ↓
按规则、质量、风险、业务流程筛选样本
    ↓
分成 Good Cases 和 Bad Cases
    ↓
Good Cases 用于 SFT，学习优质服务表现
Bad Cases 经重写后用于 DPO/RL，修复表达和策略问题
    ↓
模型升级
    ↓
继续服务用户并产生新数据
```

论文图 4 中，在线系统会综合多类上下文：

- Query and Execution：用户问题和模型执行结果。
- Tool：工具调用历史和工具反馈。
- Knowledge：业务流程、业务规则、知识库内容。
- Memory：对话历史、工具历史、用户上下文。
- Perception：信号采集、信号检索、图片识别等感知能力。
- Thinking Process / Decision-Making：模型中间推理和决策过程。
- Text and Controls：最终给用户的文本回复和控制动作。

这些信息共同进入自采样数据池，再由人工规则、流程约束、质量约束、风险约束等机制过滤。

### 样本筛选标准

论文把自采样数据分成两类：Good Cases 和 Bad Cases。核心判定维度有三个：

- Solution Correctness：解决方案是否正确。
- User Satisfaction：用户或模拟用户是否满意。
- Conversation Quality：对话质量是否高，包括自然度、推进感、重复率、安抚感等。

| 类型 | 判定标准 | 用途 |
|---|---|---|
| Good Cases | 方案正确、用户满意、对话质量高 | 用于 SFT，学习高质量服务表现 |
| Bad Cases | 方案正确但用户不满意，或对话质量差 | 重写后构造偏好对，用于 DPO/RL |
| Unused | 方案本身不正确 | 不进入训练，避免模型学习错误方案 |

这里有个细节：Bad Cases 不一定是“方案错了”。论文更关注的是“方案正确，但服务体验不好”的情况。例如模型给出了正确入口，但话术机械、重复追问、没有安抚，导致用户不满意。这类样本特别适合做偏好学习，因为它能告诉模型：同一个解决方案，怎样表达更像优质客服。

### Good Cases：自演化学习

Good Cases 的处理流程是：

```text
1. 自动获取线上 self-sampled data
2. 预处理并统一格式
3. 按解决方案类型做分层采样，保证数据多样性
4. 多维服务质量评分
5. 只保留达到或超过人工客服水平的高质量对话
6. 用知识驱动方式校验方案正确性
7. 加入 SFT 数据，训练模型学习优质服务模式
```

Good Cases 主要增强：

- Process Internalization：把高频业务流程内化进模型。
- Personification：学习更自然、更像人的表达方式。
- Generalization of Long-Tail Scenarios：覆盖长尾场景。
- Flexible Planning：学习更灵活的对话推进方式。

论文实验中，LongCat 基线 USM 1 为 52.91、USM 2 为 27.21；普通 SFT 后分别变为 38.56 和 40.61；加入 SRT Good Cases 后，USM 1 降到 28.18，USM 2 提升到 48.15。

### Bad Cases：定向修复

Bad Cases 的处理流程是：

```text
1. 从线上自采样数据中识别低质量样本
2. 分析问题类型，例如重复、表达生硬、推进失败、安抚不足
3. 用重写模型对坏例去重和优化
4. 形成“原始回复 vs 重写回复”的偏好对
5. 用于 DPO 或 RL，让模型偏向更优回复
6. 回归测试后上线进入下一轮
```

Bad Cases 主要增强：

- RL Reasoning：更稳定地按规则推理。
- Signal Comprehension：更好理解订单、配送、售后、补偿等业务信号。
- Instruction Compliance：更好遵守业务指令。
- Communication Skills：减少机械重复，提高安抚和沟通能力。

论文实验里，加入 Good Cases 和 Bad Cases 后，USM 1 从 52.91 降到 25.38，USM 2 从 27.21 提升到 52.72，重复率 RR 从 57.43 降到 20.27。也就是说，Bad Cases 的价值尤其体现在降低重复和修复低体验表达上。

### 一个例子：退款金额解释

这个例子和前文 RL 例子属于同一类退款解释场景。这里关注点不是奖励函数，而是 SRT 如何把线上对话切成 Good Case / Bad Case，并转成后续训练数据。

假设用户问：

```text
为什么我这单只退了 12 元？我明明付了 20 元。
```

系统拿到的上下文可能包括：

```text
订单实付：20 元
平台优惠券：5 元
商家优惠：3 元
可退现金：12 元
退款规则：优惠券和商家优惠不按现金退回，按规则退还或失效
用户情绪：不满，质疑退款金额
```

#### Good Case

一个高质量回复可能是：

```text
我理解你看到实付 20 元、到账 12 元会觉得不对。我帮你看了一下，这单里有 5 元平台券和 3 元商家优惠，实际可按现金退回的部分是 12 元，所以当前退款金额是按规则计算的。你可以在订单详情里的“退款明细”看到这几项拆分。如果你愿意，我也可以继续帮你核对优惠券是否有退回或补发记录。
```

这个样本会被判为 Good Case 的原因：

- 方案正确：解释了 20 元和 12 元的差额来源。
- 用户满意概率高：先承接情绪，再解释规则。
- 对话质量高：没有只甩规则，也提供下一步核对动作。

它适合进入 SFT，让模型学习“先安抚、再拆账、再给下一步”的服务模式。

#### Bad Case

一个方案正确但体验差的回复可能是：

```text
退款 12 元是正常的。优惠不退现金，请查看退款规则。
```

这个回复并没有算错，但问题在于：

- 没有解释 20 元如何拆成 12 元现金和 8 元优惠。
- 没有回应用户的不满情绪。
- 没有给出下一步操作。
- 语气生硬，容易让用户继续追问或转人工。

SRT 会把它识别成 Bad Case，然后用重写模型生成更优版本：

```text
我理解你是想确认为什么付款 20 元但只退了 12 元。我帮你拆一下：这单里有 5 元平台优惠券和 3 元商家优惠，这两部分不是按现金退回，所以现金退款金额是 12 元。你可以在订单详情的退款明细里查看拆分；如果优惠券应该退回但没有到账，我可以继续帮你核对。
```

然后构造偏好对：

```text
chosen：重写后的回复
rejected：原始生硬回复
```

这组数据可以进入 DPO/RL，让模型以后在类似退款解释场景中，更倾向于清楚拆解金额、承接情绪、给出下一步，而不是机械复述规则。

### 小结

SRT 的关键不是“把线上数据再训练一遍”，而是先判断这些线上样本是否值得学：

- 好样本用于模仿，扩大模型的优质服务行为。
- 坏样本用于对比，告诉模型哪些表达和策略应该被替换。
- 错方案样本不直接训练，避免污染模型。

这让模型迭代更像客服运营飞轮：真实服务产生数据，质检系统判断价值，训练系统吸收经验，模型上线后继续产生更好的数据。

## 5. Agent 协同层

WOWService 的 Agent 设计是“主 Agent 控制对话，子 Agent 作为专用工具被调用”。它结合了两种模式：

- Agents-as-Tools：主 Agent 保持对话控制权，按需调用专用子 Agent。
- Handoff：在高可靠流程里，允许把任务和上下文交给专用 Agent 处理。

论文强调最终由主 Agent 结合实时信号和上下文决定是否采纳子 Agent 输出，避免子 Agent 结果直接破坏对话体验。

### 外呼 Agent

外呼流程拆成四步：

```text
主对话 Agent 发起外呼请求
    → 参数解析子 Agent 提取外呼参数
    → 执行子 Agent 发起外呼
    → 结果采集子 Agent 获取外呼结果
    → 主 Agent 汇总并回复用户
```

它解决的是客服过程中需要主动联系商家、骑手或其他角色时，单纯聊天模型无法闭环执行的问题。

### 主动协同 Agent

主动协同 Agent 包含两件事：

- 对话开场时主动挖掘意图：如果系统信号足够强，就提出一个明确问题；信号不够强，就给出多个候选诉求让用户选择。
- 多场景适配：确认用户需求后，路由到对应服务场景，并检索该场景需要的信号和操作指令。

这把客服从“等用户完整描述问题”变成“根据订单、履约、售后等信号主动帮用户缩短路径”。

### 多模态理解 Agent

真实客服里用户常发图片、语音甚至视频。论文里已经把图片识别 Agent 接入端到端流程，并探索语音大模型能力，包括多模态对齐、函数调用和安全机制。

这说明智能客服不能只看文本。订单截图、骑手定位、商品图片、异常凭证等都可能是解决问题的关键上下文。

## 6. 评测与回流层

论文认为智能客服评测的难点在于：多轮对话没有唯一标准答案，模型是否“解决问题”不仅取决于最终回复，还取决于中间有没有正确理解、澄清、检索知识、调用工具、遵守规则。因此 WOWService 做的是统一评测平台，而不是单个离线 benchmark。

整体框架可以拆成两部分：

```text
评测集构造
    ↓
评测执行
    ↓
人工/模型交叉验证
    ↓
评测报告和动态榜单
    ↓
指导模型、Agent 和业务规则迭代
```

平台能力包括语料管理、版本管理、流程监控、周期性评测、动态 leaderboard。它既评基础模型，也评端到端 Agent。

### 评测集构造

评测集不是一次性静态数据，而是按真实业务场景周期性刷新。论文里分三步：

```text
1. Data Distribution Design
   根据真实线上场景设计数据分布，并随业务变化定期更新。

2. Data Sampling
   按难度、对话长度等关键维度做分层随机采样。
   其他维度用正态或均匀分布采样，保证样本有代表性。

3. Metric Design
   针对不同场景设计指标。
   使用 GSB、MOS、Perfect Rate 等指标，也会设计业务专属指标。
```

每条评测样本通常包含：

- 输入 prompt 或多轮对话上下文。
- 元数据标签，比如场景、难度、长度、关键考察点。
- 标准答案或参考方案。
- 标准答案的推理链或解释。
- 评分 rubrics。

### 评测执行

评测执行分成人工评测和模型评测：

- 人工评测：盲评，多人独立标注。每个 case 由 2-3 名评估员独立判断，并且不知道模型身份。
- 模型评测：专门的评测模型自动打分并生成理由。
- 交叉验证：自动评测结果和人工标注互相校验，分歧由专家处理。
- 评测模型迭代：分析自动评分错误，继续优化评测模型，目标是人机一致率超过 95%。

### 在线质检和数据回流

线上质检先做策略识别，再执行对应规则：

```text
对话回复 / 工具调用
    → 识别场景和服务策略
    → 检索分层规则库
    → 按优先级执行质检
    → 输出错误标签和说明
    → 实时熔断或离线回流训练
```

为了兼顾延迟和质量，它分成：

- 在线规则质检：低延迟，近 100% 精度，用于实时拦截。
- 离线精细采集：多步、多 Agent、可加人工标注，用于高质量训练数据。

论文提到质检覆盖 10 大类、36 个检查项，错误召回率达到 93.5%。

在线质检和离线评测的关系是：

```text
在线质检：
    服务中实时发现高风险问题，用于熔断、反思或快速拦截。

离线评测：
    系统性比较模型版本、Agent 流程和能力短板，用于升级决策。

数据回流：
    把线上质检、离线评测和人工复核发现的问题转成坏例、偏好对、回归集。
```

### 模型自动评测：四级评分和四阶段流水线

论文在 4.1 中提出单轮回复的四级评分：

| 分数 | 含义 |
|---|---|
| -1 | 红线问题，例如违反规则、误导用户、触碰底线 |
| 0 | 不满意，回复无效或没有解决问题 |
| 1 | 可接受，基本满足要求但不够优秀 |
| 2 | 优秀，回答完整、准确、体验好 |

自动评测不是让一个模型直接给分，而是用多 Agent 方式模拟专家评审：

```text
Stage 1：上下文聚合和输入准备
    输入历史对话、模型回复、Golden Standard、CoT、评分规则。

Stage 2：专用评审 Agent 并行打分
    -1 Point Adjudicator：判断是否有红线问题。
    2 Point Adjudicator：判断是否达到优秀标准。
    0 Point Adjudicator：判断是否无效或不满意。
    如果三个判断都不命中，则默认给 1 分。

Stage 3：高效决策路由
    如果多个评审结果不冲突，直接给出结论。
    如果有冲突，进入专家裁决。

Stage 4：专家级冲突裁决
    用更强推理能力的 Expert Adjudicator 处理模糊或冲突 case。
```

这种设计的好处是把“评分”拆成多个更清晰的二分类问题，降低单模型直接打总分的不稳定性。

### 基础模型评测

基础模型评测会剥离业务系统、外部工具和知识库，只看模型内在能力。论文构建了 Intelligent Interaction Systems Benchmark，用真实线上流量清洗数据为主，再补充人工构造数据。

评测流程是：

```text
定义场景和任务维度
    ↓
构造初始评测集
    ↓
生成或整理标准答案、参考方案、解释
    ↓
人工校验完整评测集
    ↓
同一问题采样模型三次
    ↓
人工或模型评估
    ↓
输出整体分、关键点分、质检结论和案例分析
```

基础模型能力维度包括：

- 问题理解。
- 沟通能力。
- 方案框架。
- 细节准确性。
- 表达风格。
- 语义理解。
- 知识理解。
- 真实性。
- 完整性。
- 指令遵循。
- 拟人化。
- 个性化。

核心统计指标包括：

- Overall Score：评测集中所有样本得分总和，单样本通常在 -1 到 3 分范围内。
- Availability Rate：得分为 2 或 3 的样本比例，表示答案可用率。
- Perfect Rate：得分为 3 的样本比例，表示高质量答案比例。

这个评测回答的是：不接工具、不接知识库时，模型本身是否适合客服交互。

### 端到端 Agent 评测

Agent 评测不仅看用户问题是否最终解决，还看内部执行路径是否合理：

- 是否正确理解需求。
- 是否必要时澄清。
- 是否正确调用工具。
- 是否正确使用知识库和业务规则。
- 是否在关键检查点做出正确决策。
- 成本、效率、安全性和上下游工单系统衔接是否达标。

论文强调端到端 Agent 评测要采用“双视角”：

```text
1. 用户可见视角
   用户问题是否解决，回复是否清楚，体验是否自然。

2. 内部轨迹视角
   Agent 是否正确理解需求、澄清、检索、决策、调用工具、汇总结果。
```

端到端评测需要一个贴近真实生产的沙箱环境，包含：

- 数据库和数据表。
- 用户模拟器。
- API 和工具。
- 业务规则。
- 知识库、Wiki、FAQ。
- 监控和日志。
- 上下游工单系统。

典型流程是：

```text
User Question
    ↓
Lead Agent 理解需求
    ↓
必要时向用户澄清
    ↓
检索知识库 / 查询数据库 / 调用工具
    ↓
Sub-agent 并行处理子任务
    ↓
Lead Agent 汇总结果
    ↓
回复用户或推进工单
    ↓
评测关键检查点和最终结果
```

这里的重点是：客服 Agent 不能只用最终回答打分，因为很多错误发生在不可见的工具调用、状态判断和流程推进里。

### 一个例子：骑手超时配送投诉

假设用户说：

```text
我的外卖已经超时 40 分钟了，还没送到，怎么处理？
```

#### 评测样本构造

这个 case 的评测输入不只有用户文本，还包括模拟业务环境：

```text
订单状态：配送中
预计送达时间：12:20
当前时间：13:00
骑手位置：距离用户 1.2 公里
商家出餐时间：正常
天气：暴雨
补偿规则：超时超过 30 分钟且非用户原因，可触发补偿判断
可用工具：
  - query_order_status
  - query_rider_location
  - check_compensation_eligibility
  - create_service_ticket
知识库：
  - 配送超时解释规则
  - 补偿判断规则
  - 转人工/建工单规则
```

#### 基础模型评测看什么

如果只评基础模型，会给它对话上下文和必要规则，主要看：

- 是否理解“超时配送投诉”而不是普通催单。
- 是否能先安抚用户。
- 是否知道需要核对订单状态、骑手位置和补偿资格。
- 是否表达清楚，不编造骑手或补偿结果。

一个可接受但不完美的回复可能得 1 分：

```text
很抱歉让你久等了。建议你先查看订单配送状态，如果确实超时，可以申请平台客服协助处理。
```

它方向没错，但缺少具体状态判断和下一步动作。

#### 端到端 Agent 评测看什么

端到端 Agent 需要真的走流程：

```text
1. 理解需求：识别为配送超时投诉。
2. 工具调用：查询订单状态和骑手位置。
3. 规则判断：确认超时 40 分钟，且非用户原因。
4. 补偿判断：调用补偿资格工具。
5. 回复生成：解释当前状态、安抚用户、告知处理动作。
6. 工单动作：如果需要，创建服务工单或转人工。
```

一个优秀回复和动作可能是：

```json
{
  "response": "非常抱歉让你等了这么久。我帮你查到这单预计 12:20 送达，现在已经超时约 40 分钟，骑手距离你还有约 1.2 公里。我会先为你触发超时补偿资格核验，同时继续跟进配送状态；如果骑手位置长时间不更新，我会帮你创建服务工单继续处理。",
  "tool_calls": [
    {
      "name": "query_order_status",
      "arguments": {
        "order_id": "当前订单"
      }
    },
    {
      "name": "check_compensation_eligibility",
      "arguments": {
        "order_id": "当前订单",
        "reason": "delivery_timeout"
      }
    }
  ]
}
```

#### 自动评分如何处理

四个评审 Agent 可能这样判断：

```text
-1 Point Adjudicator：
    没有发现红线问题，没有承诺不确定补偿金额。

2 Point Adjudicator：
    回复完整，正确使用订单状态、超时时长、骑手位置和补偿核验动作，命中优秀标准。

0 Point Adjudicator：
    不是无效回复。

Decision Routing：
    无冲突，给 2 分。
```

如果模型直接说“平台一定赔你 20 元”，但工具并没有返回补偿金额，-1 Point Adjudicator 可能判为误导用户或违反规则，进入红线问题。这个 case 会被回流为坏例，进入 DPO/RL 或规则质检集，用来防止模型下次越权承诺。

## 7. 关键指标

论文报告 WOWService 相比基线在核心业务指标上有明显改善：

- USM 1 降低 27.53%，该指标越低越好。
- USM 2 提升 25.51%，该指标越高越好。
- 重复率 RR 从 57.43% 降到 20.27%。
- 外呼 Agent 平均分从 57 提升到 80。
- 主动协同策略让 USM 1 从 18.2 降到 12.5，USM 2 从 48.0 提升到 58.8。

## 8. 我的理解

美团这套方案的核心经验有三点：

1. 智能客服的竞争力来自闭环工程，而不只是模型参数规模。
   线上质检、坏例回流、SRT、DPO、RL、回归测试和评测平台共同决定系统能否长期稳定变好。

2. 业务知识要进入系统全链路。
   只靠 RAG 容易停留在“查到知识”，但客服还需要判断知识是否适用、遵守流程、执行工具、安抚用户。论文把知识同时放进训练数据、prompt、检索、CoT、奖励和质检里，这更接近工业系统需要的形态。

3. Agent 的价值在于流程闭环和专用能力分工。
   外呼、主动协同、多模态理解都不是单轮问答能力，而是服务执行能力。主 Agent 负责用户体验和整体决策，子 Agent 负责特定任务，这比一个模型硬扛所有流程更可控。

## 9. 可迁移到其他客服系统的技术框架

如果抽象成通用智能客服架构，可以按下面建设：

```text
1. 业务知识工程
   原子知识、流程规则、工具 schema、场景标签

2. 数据工程
   历史对话、人工客服样本、知识生成样本、线上自采样、坏例库

3. 模型工程
   CPT 保领域能力，SFT 对齐流程，DPO 修坏例，RL 优化规则遵循和表达质量

4. 推理工程
   RAG 检索、知识可用性判断、工具调用、状态信号、对话历史和记忆

5. Agent 工程
   主对话 Agent + 外呼/多模态/主动意图/工单/补偿等专用 Agent

6. 评测工程
   基础能力评测、自动质检、端到端沙箱、人工盲评、回归测试

7. 运营闭环
   线上监控、实时熔断、离线坏例采集、标注与重写、模型版本迭代
```
