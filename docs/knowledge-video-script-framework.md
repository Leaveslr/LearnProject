# 知识视频脚本生成框架：概念、例子、判断题

## 结论

是的，视频脚本需要包含“概念、例子、练习题”，但顺序和占比要更精确：

```text
少量概念建立地图 -> 一个例子贯穿机制 -> 判断题证明用户真的懂了
```

不要把它做成三段割裂内容。真正有效的脚本，是每个概念都回到同一个例子，每个练习题都验证用户能否解释“为什么这样做”。

## 标准脚本结构

### 1. Hook：先说困惑

目标：让用户知道这个知识点解决什么痛点。

例：

```text
交叉熵到底在扣什么分？
```

### 2. 最小概念：只给地图

目标：只讲输入、输出、目标，不展开所有术语。

例：

```text
交叉熵看的是：模型给正确 token 的概率够不够高。
```

### 3. 贯穿例子：固定一个输入

目标：让用户有一个一直抓得住的心智锚点。

例：

```text
上下文是“我今天很”，真实下一个 token 是“开心”。
```

### 4. 机制拆解：每一步都回到例子

目标：把抽象流程变成具体动作。

例：

```text
模型先给候选 token 打 logits 分数；softmax 把分数变成概率；
交叉熵只盯“开心”的概率；概率越低，loss 越大。
```

### 5. 关键细节：补会卡住的地方

目标：只补真正影响理解的细节。

例：

```text
P=0.90 时 loss 约 0.11；P=0.30 时约 1.20；P=0.01 时约 4.60。
```

这类数字可以让用户建立大小直觉，而不是只背“概率越低 loss 越大”。

### 6. 反事实：解释为什么要这样做

目标：让用户知道不是“规定如此”，而是“这样设计有理由”。

例：

```text
如果不取 log，长句概率要连续相乘，数值会越来越小；
取 log 后，每一步 loss 可以相加，训练更稳定。
```

### 7. 判断题：验证真懂

目标：检查用户能不能判断对错和原因。

合格判断题：

```text
如果 P(正确 token) 从 0.3 变成 0.7，loss 会怎么变？
如果 loss mask 错了，模型会学错什么？
PPL 低为什么不等于任务一定成功？
```

不合格练习题：

```text
交叉熵公式是什么？
softmax 叫什么？
```

这类题只检查背诵，不检查理解。

### 8. 三句总结：收束成可复述模型

目标：让用户离开视频后还能复述。

例：

```text
logits 经 softmax 变概率。
交叉熵惩罚不相信正确 token。
训练就是不断把正确答案的概率推高。
```

## 生成脚本时的硬性通过标准

一个视频只有在用户能回答下面三个问题时，才算通过：

1. 它是怎么回事：这个概念解决什么问题，输入输出是什么？
2. 细节是什么：关键公式、模块或流程每一步是什么意思？
3. 为什么这么做：换一种做法会坏在哪里，指标什么时候会误导？

如果不能回答第 3 个问题，说明脚本还停在“讲概念”，没有到“真正懂”。

## 验证样本

已用 `用一个例子讲懂交叉熵` 验证这个框架：

- 贯穿例子：`我今天很 -> 开心`
- 概念地图：交叉熵惩罚模型不相信正确 token
- 机制拆解：logits -> softmax -> probability -> `-log P(开心)` -> backward update
- 关键细节：`P=0.90/0.30/0.01` 的 loss 数字直觉
- 判断题：概率升高 loss 下降、mask 决定训练目标、PPL 不等于任务成功
