# 知识视频脚本生成框架：概念、例子、例题

## 结论

一个视频要把知识点讲清楚，脚本应该串成一个完整学习闭环：

```text
先讲概念 -> 再讲例子 -> 再讲例题 -> 最后总结
```

这里的关键是“串起来”，不是三段割裂内容：

- 概念：告诉用户这个知识点是什么、解决什么问题、输入输出是什么，以及它在系统里扮演什么角色。
- 例子：用一个具体例子把概念跑通，让用户知道细节怎么发生。
- 例题：换一个相似但不完全相同的小题，让用户当场应用，验证自己是否真正懂了。
- 总结：把视频收束成 2-3 条能迁移的判断规则。

判断题可以放在例题里，但它只是例题的一种形式。最终目标不是让用户背公式，而是能跟着例题判断“为什么这样做”。

## 标准脚本结构

### 1. Hook：先说困惑

目标：让用户知道这个知识点解决什么痛点。

例：

```text
交叉熵到底在扣什么分？
```

### 2. 最小概念：只给地图

目标：只讲输入、输出、目标，不展开所有术语。

最小概念必须先回答四个问题：

```text
它是什么？
它解决什么问题？
它看什么输入，给什么输出？
它在整个系统里负责什么？
```

例：

```text
交叉熵不是模型结构，而是训练时的评分规则。
它把“正确答案”和“模型给出的一堆概率”变成一个扣分。
```

### 3. 贯穿例子：固定一个输入

目标：让用户有一个一直抓得住的心智锚点。

例：

```text
上下文是“我今天很”，真实下一个 token 是“开心”。
```

### 4. 机制拆解：每一步都回到例子

目标：把抽象流程变成具体动作。

例：

```text
模型先给候选 token 打 logits 分数；softmax 把分数变成概率；
交叉熵只盯“开心”的概率；概率越低，loss 越大。
```

### 5. 关键细节：补会卡住的地方

目标：只补真正影响理解的细节。

例：

```text
P=0.90 时 loss 约 0.11；P=0.30 时约 1.20；P=0.01 时约 4.60。
```

这类数字可以让用户建立大小直觉，而不是只背“概率越低 loss 越大”。

### 6. 反事实：解释为什么要这样做

目标：让用户知道不是“规定如此”，而是“这样设计有理由”。

例：

```text
如果不取 log，长句概率要连续相乘，数值会越来越小；
取 log 后，每一步 loss 可以相加，训练更稳定。
```

### 7. 例题：让用户当场应用

目标：换一个小题，让用户用刚学到的机制自己走一遍。

例题必须和前面的例子同构，但不能完全一样。这样用户不是复述，而是在迁移。

讲交叉熵时，前面例子可以是：

```text
上下文：“我今天很”
正确 token：“开心”
```

后面的例题可以换成：

```text
上下文：“天气非常”
正确 token：“好”
模型给“好”的概率从 0.2 提升到 0.6，loss 会怎么变？为什么？
```

合格例题要检查三件事：

- 会不会代入：能不能找到正确 token 的概率。
- 会不会判断：概率变高，loss 为什么下降。
- 会不会解释：训练为什么要推动正确 token 概率上升。

不合格例题：

```text
请背出交叉熵公式。
softmax 的英文是什么？
```

这类题只检查记忆，不检查理解。

### 8. 总结：收束成可迁移规则

目标：让用户离开视频后还能复述。

例：

```text
概念：交叉熵是训练扣分规则。
例子：提高正确 token 概率，loss 会下降。
例题：换一个句子，也要先找正确 token 的概率。
```

总结不要写成抽象口号，要写成“下次遇到新题时能怎么判断”的规则。如果总结页出现长句重叠，优先改成三行 `trace`：左边是规则标签，右边是短解释。

## 生成脚本时的硬性通过标准

一个视频只有在用户能完成下面四件事时，才算通过：

1. 它是怎么回事：这个概念解决什么问题，输入输出是什么？
2. 细节是什么：关键公式、模块或流程每一步是什么意思？
3. 例子怎么跑：能否跟着一个具体例子把机制走完？
4. 例题会不会做：换一个相似小题，能否判断结果并解释原因？

如果不能完成第 4 点，说明视频只是“讲懂了例子”，还没有让用户真正学会迁移。

## 评估与迭代检查

### 用户视角评估

评估时不要只问“讲得对不对”，要模拟一个完全没学过的用户：

1. 看完概念段，能不能说出它是什么，而不是只记住名字？
2. 看完例子段，能不能复述例子每一步为什么发生？
3. 看完例题段，能不能在新输入上做同样判断？
4. 看完总结段，能不能带走 2-3 条下次可用的规则？

### 迭代优先级

发现问题时按这个顺序改：

1. 先改概念入口：如果用户不知道它是什么，后面的公式和例子都不稳。
2. 再改贯穿例子：如果例子没有跑完整，例题会变成猜答案。
3. 再改例题：如果例题只是背诵，用户没有真正迁移。
4. 最后改画面：字幕压屏、短文本被拉大、总结动画重叠，都会直接降低学习感。

## 验证样本

已用 `概念例子例题讲懂交叉熵` 验证这个框架：

- 概念入口：交叉熵是训练时的扣分规则，不是模型结构。
- 贯穿例子：`我今天很 -> 开心`，展示 P(开心) 从 0.30 到 0.72，loss 为什么下降。
- 机制拆解：logits -> softmax -> probability -> `-log P(开心)` -> backward update。
- 例题验证：换成 `天气非常 -> 好`，判断 P(好) 从 0.20 到 0.60 时 loss 如何变化。
- 总结规则：正确概率越高 loss 越低；mask 决定训练目标；PPL 低不等于任务一定成功。
- 最终评估：94/100。
