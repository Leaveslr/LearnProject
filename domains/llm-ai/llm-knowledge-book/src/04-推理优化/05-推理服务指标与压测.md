# 推理服务指标与压测

## 一句话结论

部署 LLM 不能只说“模型能跑起来”，还要衡量首 token 延迟、单 token 延迟、吞吐、并发、显存和成本。

## 1. 为什么需要服务指标

同一个模型在不同部署方式下，体验可能完全不同：

- 用户等首 token 太久，会感觉卡。
- 生成速度太慢，会影响对话体验。
- 并发一高就 OOM，说明容量规划不够。
- 吞吐不高，单位成本就会很贵。

工程上要把这些体验变成可测指标。

## 2. TTFT

TTFT 是 Time To First Token，表示从请求发出到第一个 token 返回的时间。

TTFT 主要受这些因素影响：

- prompt 长度。
- prefill 计算。
- 排队时间。
- prefix cache 命中率。
- 调度策略。
- 模型大小和硬件。

长 prompt 的 TTFT 通常更高，因为 prefill 要处理完整输入。

## 3. TPOT

TPOT 是 Time Per Output Token，表示 decode 阶段每生成一个 token 的平均耗时。

它影响“流式输出速度”。

TPOT 主要受：

- KV Cache 读取。
- 显存带宽。
- batch 调度。
- 模型大小。
- 量化方式。
- attention 实现。

## 4. Throughput

吞吐可以从两个角度看：

- requests per second。
- tokens per second。

LLM 服务更常看 tokens/s，因为不同请求输入输出长度差异很大。

要区分：

- input tokens/s。
- output tokens/s。
- total tokens/s。

## 5. 并发与排队

并发不是越高越好。并发提高后：

- batch 变大，吞吐可能提高。
- 单个请求延迟可能变高。
- KV Cache 显存增长。
- 排队时间增加。

服务优化要在吞吐和延迟之间做取舍。

## 6. 成本指标

常见成本口径：

- 每 1K token 成本。
- 每请求平均成本。
- 单 GPU 每小时产出 token 数。
- 峰值并发下 GPU 利用率。
- cache 命中带来的节省。

成本不是只看模型参数量，还要看：

- 输入输出长度。
- batch 效率。
- 量化。
- 硬件价格。
- 空闲率。
- 重试率。

## 7. 压测要测什么

基础压测维度：

- 不同 prompt 长度。
- 不同输出长度。
- 不同并发数。
- 不同 batch 策略。
- 是否开启 prefix cache。
- 是否量化。
- 不同模型大小。

建议记录：

- P50 / P95 / P99 TTFT。
- P50 / P95 / P99 total latency。
- output tokens/s。
- GPU memory。
- GPU utilization。
- OOM 和错误率。

## 8. 常见优化手段

| 问题 | 优化方向 |
| --- | --- |
| TTFT 高 | prefix cache、缩短 prompt、提高 prefill 吞吐 |
| TPOT 高 | 量化、GQA/MQA、优化 KV Cache、换推理框架 |
| 并发低 | PagedAttention、continuous batching、容量规划 |
| 成本高 | 小模型、蒸馏、量化、cache、路由 |
| 长尾延迟高 | 限流、队列隔离、请求分桶、超时控制 |

## 9. 面试追问

### Q1：TTFT 和 TPOT 的区别？

TTFT 是首 token 延迟，主要受 prefill 和排队影响；TPOT 是每个输出 token 的生成耗时，主要反映 decode 阶段速度。

### Q2：为什么吞吐提高可能导致延迟变差？

更大的 batch 能提高 GPU 利用率和 tokens/s，但请求可能排队更久，单请求延迟和尾延迟会上升。

### Q3：压测 LLM 服务为什么不能只看 QPS？

因为不同请求 token 长度差异很大，QPS 无法反映真实计算量，需要结合 input/output tokens/s、延迟和显存。

## 学习检查

- TTFT、TPOT、throughput、并发、成本分别代表什么。
- 为什么 LLM 服务要按 token 而不只按请求评估。
- 如何设计一个基本压测方案。
