## 二、注意力机制对比

### 2.1 四种注意力类型详解

| 类型 | 全称 | 代表模型 | 内存效率 | 质量 | 实现复杂度 |
|------|------|----------|----------|------|------------|
| **MHA** | 多头注意力 | GPT-1/2 | ❌ 最低 | 基准 | ⭐ 简单 |
| **MQA** | 多查询注意力 | - | ⭐ 中等 | 略低 | ⭐ 简单 |
| **GQA** | 分组查询注意力 | Llama 2/3/4 | ⭐⭐ ~4x 降低 | 99% MHA | ⭐⭐ 中等 |
| **MLA** | 多头潜在注意力 | DeepSeek V3, Kimi K2 | ⭐⭐⭐ ~50% GQA | 匹配/超越 | ⭐⭐⭐ 复杂 |
| **滑动窗口** | 局部+全局注意力 | Gemma 3, Mistral | ⭐⭐⭐ 线性 | 局部优秀 | ⭐⭐ 中等 |

### 2.2 GQA vs MLA 深度对比

#### GQA (Grouped Query Attention)
```
原理: 多 Query 头共享一组 K/V 头

配置示例 (Llama 4):
- Query 头数: 32
- KV 头数: 8 (每4个Query头共享1个KV头)
- 内存节省: ~4x
```

#### MLA (Multi-head Latent Attention) - DeepSeek V3 首创
```
原理: 将 K/V 压缩到低维潜在空间，推理时再投影回原始维度

配置示例 (DeepSeek V3):
- 潜在维度: 512 (远小于原始 8192)
- 投影回原始维度: 8192
- 内存节省: ~50% 比 GQA 更好

核心公式:
K_compressed = W_K @ x @ W_down  # 压缩到低维
V_compressed = W_V @ x @ W_down
K = W_up @ K_compressed           # 推理时展开
V = W_up @ V_compressed
```

### 2.3 DeepSeek 内部测试结论

> ⚠️ **重要发现**: DeepSeek 内部测试显示 GQA 性能反而略低于标准 MHA，而 MLA 能超越 MHA —— 这促使他们坚定选择 MLA。

```python
# 注意力机制性能对比 (DeepSeek 内部测试)
性能排序: MLA > MHA > GQA
内存排序: MLA > GQA > MHA

结论: MLA 在性能和内存两个维度都占优
```

### 2.4 滑动窗口注意力 (Gemma 3)

```
架构设计:
- 局部注意力窗口: 1024 tokens
- 全局注意力: 所有 tokens
- 压缩比例: 5:1

优势: 27B 模型可在消费级硬件 (RTX 4090) 运行
```

## 三、MoE 架构设计

### 3.1 MoE 核心原理

```
稀疏激活: 每个 token 只激活少数专家

传统 Dense: 所有参数都参与计算
MoE: 只有选中的"专家"参与计算

参数量 ↑ 但 计算量 ≈ 小模型
```

### 3.2 主流 MoE 模型对比

| 模型 | 专家总数 | 激活专家数 | 活跃参数 | 特殊设计 |
|------|---------|-----------|---------|----------|
| **DeepSeek V3** | 256 | 9 (含1共享) | 37B | 共享专家捕获通用模式 |
| **Llama 4 Maverick** | 128 | 2 | 17B | 交替密集/MoE 层 |
| **Qwen3 235B** | 8 | 8 | 22B | 无共享专家设计 |
| **Mixtral 8x7B** | 8 | 2 | 12B | 经典 MoE |

### 3.3 DeepSeek V3 MoE 设计亮点

```python
# DeepSeek V3 MoE 配置
total_experts = 256
shared_experts = 1  # 每个token都激活
routed_experts = 8  # 路由选中的专家

# 共享专家的作用
shared_knowledge = 所有token都学习
# 释放其他专家专注细分知识领域

# 专家路由
router = TopK(routed_experts)  # 每个token选8个专家
```

### 3.4 Llama 4 交替 MoE 设计

```
层1: 密集 FFN (标准 Transformer)
层2: MoE FFN (专家混合)
层3: 密集 FFN
层4: MoE FFN
...

优势: 
- 平衡模型容量和计算效率
- 密集层提供稳定的特征提取
- MoE 层提供稀疏的专家知识
```

### 3.5 Qwen3 混合架构

```
创新点: 结合密集层与 MoE 层

移除共享专家的原因:
- 专家数增加到256后，共享专家的收益降低
- 简化设计，提升路由效率
```

## 四、归一化策略创新

### 4.1 归一化策略对比

| 策略 | 训练稳定性 | 最终性能 | 实现 | 代表模型 |
|------|------------|----------|------|----------|
| **Pre-Norm** | ⭐⭐⭐ 优秀 | ⭐⭐ 良好 | 简单 | Llama, GPT-3+ |
| **Post-Norm** | ⭐ 困难 | ⭐⭐⭐ 最佳 | 简单 | OLMo 2 |
| **QK-Norm** | ⭐⭐⭐ 优秀 | ⭐⭐ 良好 | 中等 | OLMo 2 |
| **Pre+Post 双保险** | ⭐⭐⭐ 优秀 | ⭐⭐⭐ 最佳 | 复杂 | Gemma 3 |

### 4.2 Pre-Norm vs Post-Norm

```python
# Pre-Norm (先归一化)
x = LayerNorm(x)
x = Attention(x) + x  # 残差连接在归一化之后

# Post-Norm (后归一化)
x = Attention(x) + x
x = LayerNorm(x)  # 归一化在残差之后

# OLMo 2: Post-Norm + QK-Norm
x = Attention(QK_Norm(x)) + x
x = PostNorm(x)
```

### 4.3 QK-Norm 原理

```
目的: 防止注意力分数爆炸

原理: 在计算注意力前，对 Q 和 K 做归一化
attn_scores = (Q_norm @ K_norm.T) / sqrt(d_k)

效果: 训练稳定性显著提升
```

### 4.4 Gemma 3 双归一化

```python
# Gemma 3: Pre-Norm + Post-Norm 双保险
x = PreNorm(x)                    # 第一步归一化
x = Attention(x) + x              # 注意力
x = PreNorm(x) + PostNorm(x)      # 第二步归一化 (双保险)
```

## 五、部署场景选择

### 5.1 场景化推荐

| 应用场景 | 推荐模型 | 核心优势 |
|----------|----------|----------|
| 🔬 研究与实验 | OLMo 2, SmolLM3 | 完全透明、文档完善、教育导向 |
| 🏭 生产部署 | Llama 4, Gemma 3 | 经过验证、经过优化、生态完善 |
| ⚡ 极致效率 | DeepSeek V3, Qwen3 | MLA/MoE、低推理成本 |
| 💻 本地部署 | Gemma 3, Qwen3 小型 | 滑动窗口、消费级硬件友好 |
| 🚀 最高能力 | DeepSeek V3, Kimi K2 | 最大参数、最强能力 |

### 5.2 硬件需求对比

| 场景 | 推荐模型 | 硬件需求 | 成本估算 |
|------|----------|----------|----------|
| ☁️ 云端部署 | DeepSeek V3, Llama 4 | 8xH100/A100 | $2-5/小时 |
| 🏢 企业本地 | Gemma 3, Qwen3 | 4xA6000/4090 | $50-200K |
| 💻 开发者本地 | SmolLM3, Gemma 3 小型 | RTX 4090/M3 Max | $1-5K |
| 📱 边缘部署 | 量化 Gemma 3 | 移动GPU/NPU | 低成本 |

### 5.3 架构选择决策树

```
需要最高能力?
├── Yes → DeepSeek V3 (671B) / Kimi K2 (1万亿)
└── No
    ├── 需要本地部署?
    │   ├── Yes → Gemma 3 (滑动窗口) / SmolLM3
    │   └── No
    │       ├── 需要透明可复现?
    │       │   ├── Yes → OLMo 2
    │       │   └── No
```

## 六、面试高频问题

### Q1: 为什么 DeepSeek V3 选择 MLA 而不是 GQA？

**参考答案**:

DeepSeek 团队做了大量消融实验，发现几个关键点：

1. **性能对比**: MLA 在 benchmarks 上略优于 GQA
2. **内存效率**: MLA 通过低秩压缩，内存消耗比 GQA 更低
3. **理论优势**: MLA 的压缩-展开机制能更好地捕获 token 间的依赖关系

> "我们测试了 GQA，发现它的性能反而略低于标准 MHA。但 MLA 能够超越 MHA，这让我们坚定选择了 MLA。"

### Q2: MoE 的负载均衡问题如何解决？

**参考答案**:

主要策略：

1. **辅助损失函数**: 添加负载均衡损失惩罚不均匀分配
2. **容量因子**: 设置专家处理 token 的最大容量
3. **随机路由**: 以小概率随机选择专家，防止崩溃
4. **DeepSeek 的探索**: 共享专家设计分担通用知识

```python
# 负载均衡损失
load_balance_loss = α * Σ(top_k * expert_fraction)
# α: 超参数，通常 0.01-0.05
```

### Q3: Pre-Norm vs Post-Norm 的选择？

**参考答案**:

| 场景 | 推荐 | 原因 |
|------|------|------|
| **大模型训练** | Pre-Norm | 训练更稳定，梯度流动好 |
| **小模型优化** | Post-Norm | 最终性能更优 (需配合 QK-Norm) |
| **平衡场景** | Pre+Post 双保险 | Gemma 3 采用此策略 |

### Q4: 滑动窗口注意力如何处理长距离依赖？

**参考答案**:

Gemma 3 的解决方案：

1. **局部窗口**: 1024 tokens 局部注意力
2. **全局 tokens**: 定期选择全局 tokens 做全注意力
3. **5:1 压缩比**: 牺牲部分长距离信息，换取效率

> 适用于：代码生成、短文本任务
> 不适用于：需要完全长距离依赖的推理任务

### Q5: 如何选择模型做生产部署？

**参考答案**:

| 优先级 | 推荐模型 | 评估维度 |
|--------|----------|----------|
| 延迟最低 | Llama 4, Gemma 3 | GQA 推理速度快 |
| 成本最低 | DeepSeek V3, Qwen3 | MoE 稀疏激活 |
| 质量最高 | DeepSeek V3 | 最大活跃参数 |
| 本地部署 | Gemma 3 小型 | 滑动窗口 + 量化 |

**实际选择流程**:

```
1. 确定核心需求 (质量/速度/成本)
2. 评估硬件约束
3. 基准测试关键指标
4. A/B 测试上线
```
