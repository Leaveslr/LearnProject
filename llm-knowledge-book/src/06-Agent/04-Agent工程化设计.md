# Agent 工程化设计

## 一句话结论

Agent 工程化的核心不是“让模型调用工具”，而是让模型在可控流程里规划、执行、观察、恢复、评估，并且能被追踪和约束。

## 1. Workflow vs Agent

Workflow 是人预先写好流程，模型只在某些节点做判断或生成。

Agent 是模型在一定边界内动态决定下一步做什么。

| 类型 | 特点 | 适合场景 |
| --- | --- | --- |
| Workflow | 稳定、可控、易测试 | 流程明确的业务 |
| Agent | 灵活、可探索、成本高 | 任务开放、路径不固定 |

工程建议：能用 workflow 解决，就不要过早升级成 Agent。

## 2. Agent 的核心组件

一个生产级 Agent 至少要考虑：

- 任务目标。
- 状态管理。
- 工具列表。
- 工具 schema。
- 规划策略。
- 执行循环。
- 错误恢复。
- 人工确认。
- 轨迹记录。
- 评估集。

## 3. Tool Schema

工具 schema 要清楚描述：

- 工具能做什么。
- 参数类型。
- 参数约束。
- 返回结构。
- 失败情况。
- 权限边界。

坏 schema 会导致：

- 参数乱填。
- 工具误用。
- 错误难恢复。
- 安全风险。

## 4. 状态与记忆

Agent 的 memory 不能简单等同于长上下文。

常见层次：

- short-term memory：当前任务过程。
- long-term memory：跨任务偏好、事实、历史结果。
- episodic memory：过去任务轨迹。
- semantic memory：可检索知识。

工程上要明确：

- 什么能写入记忆。
- 谁能读取记忆。
- 记忆何时过期。
- 错误记忆如何修正。

## 5. Human-in-the-loop

高风险步骤应该加入人工确认，例如：

- 付款。
- 删除数据。
- 发邮件。
- 发布内容。
- 修改生产配置。
- 访问敏感信息。

HITL 不是降低自动化，而是把风险边界显式化。

## 6. 错误恢复

Agent 常见失败：

- 工具调用失败。
- 参数错误。
- 陷入循环。
- 计划过大。
- 中间状态丢失。
- 幻觉工具能力。
- 权限越界。

常见恢复策略：

- 工具返回结构化错误。
- 重试次数限制。
- fallback 工具。
- 计划重写。
- 超时中断。
- 人工接管。
- 状态回滚。

## 7. Observability

Agent 必须能看见执行轨迹。

至少记录：

- 用户输入。
- 模型思考摘要或决策理由。
- 工具调用参数。
- 工具返回。
- 每步耗时。
- token 成本。
- 最终结果。
- 失败原因。

没有 trace，就很难调试 Agent。

## 8. Agent Eval

Agent 评估不能只看最终答案。

要同时看：

- task success rate。
- tool call accuracy。
- step efficiency。
- cost。
- latency。
- recovery rate。
- human intervention rate。
- safety violation。

对于复杂任务，还要评估轨迹是否合理。

## 9. 多 Agent 什么时候有用

多 Agent 适合：

- 任务天然可拆角色。
- 需要互相审查。
- 子任务工具集差异大。
- 并行探索有收益。

不适合：

- 简单任务。
- 低延迟任务。
- 没有清晰协调机制。
- 成本敏感场景。

多 Agent 可能更慢、更贵、更难调试。

## 10. 面试追问

### Q1：什么时候用 workflow，什么时候用 Agent？

流程明确、稳定性要求高时优先 workflow；任务开放、路径不固定、需要动态工具选择时才考虑 Agent。

### Q2：Agent 如何避免死循环？

设置最大步数、状态检查、重复动作检测、目标进度评估、超时中断和人工接管。

### Q3：如何评估 Agent？

不仅看最终成功率，还要看工具调用正确率、轨迹合理性、成本、延迟、恢复能力和安全违规。

## 学习检查

学完本章后，应该能讲清：

- Agent 与 workflow 的边界。
- tool schema、memory、HITL、trace 各自解决什么问题。
- 为什么 Agent 评估必须看执行过程。
